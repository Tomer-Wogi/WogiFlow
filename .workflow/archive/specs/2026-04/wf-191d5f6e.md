# [wf-191d5f6e] Main-mode question classifier auto-defers task-boundary restart

## User Story
**As a** WogiFlow user running Claude Code in main/solo mode with `taskBoundaryReset.enabled: true`
**I want** the task-boundary restart to auto-defer when the AI ends a turn with an open question to me
**So that** my answer isn't orphaned by a context reset when the AI forgets to call `flow ask` first

## Description
Orphaned-question bug observed 2026-04-24: the prior session's last reply asked "Confirm this approach, or want a different split?" but did not call `flow ask`. The Stop hook fired `consumeAndTriggerRestart()`, `hasPendingQuestion()` returned false, SIGTERM was sent, the wogi-claude wrapper restarted Claude with fresh context, and the user's next reply ("go with 1") landed in a session with no memory of the question.

The pending-question deferral infrastructure already works — `task-boundary-reset.js:166-174` correctly honors `pending-question.json`. The gap is the **human-discipline dependency**: main mode trusts the AI to call `flow ask` before ending a turn with a question. Worker mode already closes this gap via `flow-worker-question-classifier.js` (Haiku semantic detection at Stop-hook time). This story ports that safety net to main mode so the same class of bug is mechanically prevented.

## Acceptance Criteria

### Scenario 1: Main-mode turn ends with open question, no flow-ask call
**Given** `mainModeQuestionClassifier.enabled: true`, `ANTHROPIC_API_KEY` set, main-mode session with `task-just-completed` marker present
**And** the final assistant message ends with an open user-facing question (e.g., "Option A or B?")
**And** `pending-question.json` is absent
**When** the Stop hook calls `consumeAndTriggerRestart()`
**Then** the classifier runs, returns `{ isUserQuestion: true, confidence >= minConfidence }`
**And** the pending-question marker is auto-written via `markQuestionPending()`
**And** the function returns `{ triggered: false, reason: 'auto-deferred-question-detected' }`
**And** SIGTERM is NOT sent; the task-just-completed marker STAYS in place for next Stop hook

### Scenario 2: Main-mode turn with no question proceeds normally
**Given** `mainModeQuestionClassifier.enabled: true`, main-mode session, task-just-completed marker present
**And** the final assistant message is a statement or completion report (no open question)
**When** `consumeAndTriggerRestart()` runs
**Then** classifier returns `{ isUserQuestion: false }` (or below confidence threshold)
**And** restart proceeds normally: marker consumed, flag written, SIGTERM sent to parent

### Scenario 3: Worker-mode behavior unchanged
**Given** workspace worker mode (`WOGI_WORKSPACE_ROOT` set + `WOGI_REPO_NAME !== 'manager'`)
**When** the Stop hook's existing worker-classifier path runs
**Then** the new main-mode path is SKIPPED (mode detection gates this)
**And** existing worker-mode block-with-channel-dispatch flow fires exactly as before

### Scenario 4: Fail-open on classifier failure
**Given** main-mode session, task-just-completed marker present
**When** any of: `ANTHROPIC_API_KEY` missing / transcript path missing / transcript unreadable / `callModel` throws / JSON parse fails / dangerous keys in response
**Then** classifier returns `{ classified: false, reason: <specific> }`
**And** restart proceeds normally (fail-open — a silent restart is recoverable; a stuck-forever restart block is not)

### Scenario 5: Existing manual `flow ask` path still works
**Given** main-mode session, AI explicitly called `flow ask "<q>"` before ending turn
**And** `pending-question.json` already exists
**When** `consumeAndTriggerRestart()` runs
**Then** the existing `hasPendingQuestion()` check short-circuits before the classifier runs
**And** restart deferred with reason `pending-question-deferred` (existing behavior, NOT `auto-deferred-question-detected`)

## Technical Notes

- **Files touched**:
  - `scripts/flow-worker-question-classifier.js` — add a `mode: 'worker'|'main'` parameter; branch prompt selection inside. Export a new `classifyQuestion` alias alongside existing `classifyWorkerQuestion` (preserve worker API for zero-signature-break).
  - `scripts/hooks/core/task-boundary-reset.js` — in `consumeAndTriggerRestart()`, AFTER `hasPendingQuestion()` fails but BEFORE `checkPreconditions()`: if `mainModeQuestionClassifier.enabled` AND not in worker mode, run classifier in main mode. On `blocked: true` result, call `markQuestionPending()` and return `{ triggered: false, reason: 'auto-deferred-question-detected' }`.
  - `scripts/flow-config-defaults.js` — add top-level `mainModeQuestionClassifier: { enabled: true, minConfidence: 70, model: 'anthropic:claude-3-5-haiku-latest' }` plus `_comment_mainModeQuestionClassifier` explaining the purpose.
  - `scripts/hooks/entry/claude-code/stop.js` — pass transcript path through to `consumeAndTriggerRestart()` and `await` it (function becomes async). Stop hook already has transcript path (worker classifier at line 334).
- **Async handling**: `classifyWorkerQuestion` is async. Make `consumeAndTriggerRestart` async; propagate `await` through Stop hook entry.
- **Mode detection**: invert the existing worker-mode detector. If `!isWorkerMode` AND `mainModeQuestionClassifier.enabled` → main-mode path.
- **Prompt for main mode**: differs from worker-mode prompt. Main-mode prompt says "the AI should have called `flow ask` first to defer the task-boundary restart — this classifier is the safety net." Same classification target (is-user-question), same fail-open pattern, same JSON output shape.
- **Confidence threshold default 70**: matches existing worker default.

**Rule placement (per decisions.md 2026-04-20)**: enforcement code ships in `scripts/` — the RULE text must also ship to end users via `.workflow/templates/partials/methodology-rules.hbs`. This story's deliverables include a new methodology-rule entry describing the main-mode classifier contract, added to the partial and synced via `flow bridge sync`. Skipping this re-creates the exact shadow pattern the 2026-04-20 rule was written to prevent.
