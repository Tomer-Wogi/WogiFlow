# wf-b2532240: Phase T1 — Teams Foundation

## User Story

As a WogiFlow developer, I want to build the Teams Foundation (auth, orgs, projects, CLI device auth) so that the @wogiflow/teams paid extension can enable team collaboration features.

## Context

- **Repo**: Primarily `wogiflow-cloud` (private monorepo), minimal changes to `wogi-flow` (free package)
- **Branch**: `feature/teams-t1` in both repos
- **Infrastructure**: AWS Lambda + API Gateway V2 + RDS PostgreSQL 16.6 + Secrets Manager
- **Existing patterns**: Lambda handler, validate.js, response.js, admin-auth.js, db.js
- **Domain**: api.wogi.ai

## Architecture Decisions

1. **Custom OAuth over AWS Cognito** — Avoids vendor lock-in, better multi-tenant control
2. **Hybrid token strategy**: JWT (RS256, 15min TTL) for API access + Opaque refresh tokens (30 days, DB-stored, revocable)
3. **CLI auth**: RFC 8628 Device Authorization Grant (same flow as GitHub CLI)
4. **Token storage**: `~/.config/wogiflow/auth.json` with 0600 permissions
5. **OAuth providers**: GitHub + Google (email/password deferred to T2)
6. **Password hashing**: Not needed for T1 (OAuth-only, no email/password auth yet)

## Acceptance Criteria

### Scenario 1: Database schema — Teams foundation tables
Given the existing community DB (001_community.sql, 002_pgvector_indexes.sql)
When migration 003_teams.sql is applied
Then tables `users`, `teams`, `team_members`, `projects`, `device_codes`, `oauth_state`, `refresh_tokens`, `audit_log` exist with proper indexes, constraints, and foreign keys

### Scenario 2: JWT auth library — sign and verify tokens
Given a valid user ID and scopes
When `generateAccessToken(userId, teamId, scopes)` is called
Then a JWT (RS256, 15min TTL, issuer: 'wogiflow') is returned
And `validateAccessToken(token)` returns `{userId, teamId, scopes}` or null

### Scenario 3: GitHub OAuth — authorize and callback
Given a user clicks "Login with GitHub" on the dashboard
When they complete the GitHub OAuth flow
Then a user record is created/updated in the `users` table
And an access token + refresh token pair is returned
And the OAuth state token is validated and consumed (one-time use)

### Scenario 4: Google OAuth — authorize and callback
Given a user clicks "Login with Google" on the dashboard
When they complete the Google OAuth flow
Then a user record is created/updated in the `users` table
And an access token + refresh token pair is returned

### Scenario 5: CLI Device Authorization — init and poll
Given a user runs `flow auth login` (or equivalent CLI command)
When the CLI calls POST /api/auth/device/init
Then a device_code and user_code (8 chars, formatted ABC-DEFGH) are returned
And the user is shown a verification URL + user code
When the user opens the URL and enters the code on the dashboard
And the CLI polls GET /api/auth/device/status/{device_code}
Then the CLI receives access + refresh tokens after approval

### Scenario 6: Token refresh endpoint
Given an expired access token and valid refresh token
When POST /api/auth/refresh is called with the refresh token
Then a new access token is returned
And the old refresh token is rotated (old invalidated, new issued)

### Scenario 7: Teams CRUD — create, list, get
Given an authenticated user
When they POST /api/teams with {name, description}
Then a new team is created with the user as owner
And GET /api/teams returns all teams the user is a member of
And GET /api/teams/:id returns team details with member list

### Scenario 8: Team member management — invite and roles
Given a team owner or admin
When they POST /api/teams/:id/members with {email, role}
Then the user is added to the team (or invite created if user doesn't exist yet)
And role must be one of: owner, admin, member, viewer
And only owners can add admins; admins can add members/viewers

### Scenario 9: Projects CRUD — create, list under team
Given a team member with write permissions
When they POST /api/teams/:id/projects with {name, description}
Then a project is created under that team
And GET /api/teams/:id/projects lists all projects in the team

### Scenario 10: CloudFormation — new Lambda functions and routes
Given the updated cloudformation.yaml
When the stack is deployed
Then new Lambda functions (auth, device-auth, teams, projects) are created
And new API Gateway routes map to the correct functions
And new secrets (google-oauth, github-oauth, jwt-signing-key) are provisioned

### Scenario 11: Dashboard — login page with OAuth buttons
Given the existing maintainer dashboard (index.html + app.js)
When a user visits the dashboard
Then they see "Login with GitHub" and "Login with Google" buttons
And after successful OAuth, they see their teams and projects
And there is a "Device Authorization" page where users can enter CLI user codes

### Scenario 12: Unit tests for auth, teams, and projects
Given the new auth, teams, and projects modules
When `node --test tests/unit/*.test.js` is run
Then all tests pass including:
- JWT sign/verify (valid token, expired token, tampered token)
- OAuth state validation (valid state, expired state, reused state)
- Team membership checks (owner, admin, member, viewer permissions)
- Device code flow (init, approve, expire, poll)
- Input validation (prototype pollution, UUID format, size limits)

## Security Requirements
- Prototype pollution checks on all input validation
- Constant-time comparison for all token/key validation
- Parameterized queries only (no string interpolation in SQL)
- OAuth state tokens: one-time use, 5-minute TTL
- JWT: RS256 signing key from Secrets Manager, 15min TTL
- Refresh tokens: cryptographically random, rotated on use
- Device codes: high-entropy device_code, human-readable user_code
- Rate limiting: 5 login attempts per 15min per IP, 5 device codes per hour per IP
- All secrets in AWS Secrets Manager with 15-min cache
