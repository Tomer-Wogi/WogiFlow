# Story: Add routing gate hook — programmatic enforcement blocking Bash before /wogi-* routing

**ID**: wf-2c28480c
**Type**: story
**Feature**: workflow
**Priority**: P0
**Complexity**: Medium
**Files to Change**: 4

## User Story

As a WogiFlow user, I want a **programmatic hook** that blocks Bash/tool execution before a `/wogi-*` command has been invoked, so that the mandatory routing rule cannot be bypassed by the AI regardless of prompt compliance.

## Description

The AI keeps bypassing the mandatory routing rule despite explicit instructions in CLAUDE.md. Text-based instructions cannot guarantee 100% compliance — the AI rationalizes "this is just a quick command" and skips routing. WogiFlow already solved this for Edit/Write operations with the task-gate (PreToolUse hook). This story adds the same pattern for Bash: a **routing gate** that blocks Bash calls when no `/wogi-*` command has been invoked first.

### Architecture

```
User message arrives
    ↓
UserPromptSubmit hook
    → If NO active task in ready.json inProgress: write .routing-pending flag
    → If active task exists: skip (follow-ups during tracked work are allowed)
    ↓
AI tries Bash("git status") before routing
    ↓
PreToolUse hook (Bash)
    → .routing-pending flag exists → BLOCK
    → Message: "Route through /wogi-start first"
    ↓
AI calls Skill("wogi-start", "push to github")
    ↓
PreToolUse hook (Skill wogi-*)
    → Clears .routing-pending flag
    ↓
AI calls Bash("git push") after routing
    → No flag → ALLOWED
```

### Key Design Decision: Active Task Bypass

When a task is in `ready.json` inProgress, the routing flag is NOT set. This handles conversational follow-ups during active work (e.g., user saying "yes" to approve a spec). The AI is already in a tracked workflow and doesn't need to re-route each follow-up message.

## Acceptance Criteria

### Scenario 1: Block Bash before routing (no active task)
Given no active task in ready.json inProgress
When the user submits a message (e.g., "push to github")
And the AI attempts to call Bash before invoking a /wogi-* skill
Then the PreToolUse hook BLOCKS the Bash call
And displays: "Route through a /wogi-* command first. Use /wogi-start to route your request."

### Scenario 2: Allow Bash after routing
Given no active task in ready.json inProgress
When the user submits a message
And the AI first invokes Skill("wogi-start", args)
And then calls Bash
Then the PreToolUse hook ALLOWS the Bash call (routing flag was cleared by Skill invocation)

### Scenario 3: Skip routing gate during active task
Given an active task exists in ready.json inProgress
When the user submits a follow-up message (e.g., "yes", "approved", "continue")
Then the routing flag is NOT set
And Bash calls are allowed without requiring a /wogi-* skill invocation

### Scenario 4: Clear flag on any /wogi-* skill
Given the routing flag is set
When the AI invokes Skill("wogi-review") or Skill("wogi-ready") or any wogi-* skill
Then the routing flag is cleared
And subsequent Bash calls are allowed

### Scenario 5: Config toggle
Given config.hooks.rules.routingGate.enabled is false
When the user submits any message
Then the routing gate is completely disabled
And Bash calls are never blocked by routing

### Scenario 6: Graceful degradation
Given the routing gate flag file cannot be read (permissions, missing directory)
Then the hook allows the Bash call (fail-open for this specific gate)
And logs a warning to stderr if DEBUG is set

## Technical Notes

### Files to Change

1. **scripts/hooks/core/routing-gate.js** (CREATE)
   - `setRoutingPending()` — writes `.workflow/state/.routing-pending` with timestamp
   - `clearRoutingPending()` — deletes the flag file
   - `isRoutingPending()` — checks if flag exists and returns boolean
   - `checkRoutingGate(toolName)` — returns `{ blocked, reason, message }` for Bash

2. **scripts/hooks/entry/claude-code/user-prompt-submit.js** (MODIFY)
   - After existing checks, call `setRoutingPending()` if no active task in inProgress
   - Import `setRoutingPending` from routing-gate core module
   - Check ready.json inProgress array (use existing `safeJsonParse`)

3. **scripts/hooks/entry/claude-code/pre-tool-use.js** (MODIFY)
   - For `Skill` tool with wogi-* skill: call `clearRoutingPending()`
   - For `Bash` tool: call `checkRoutingGate()`, block if pending
   - Add routing-gate check BEFORE strict adherence check

4. **.workflow/config.json** (MODIFY)
   - Add `hooks.rules.routingGate: { enabled: true }` config key

### Patterns to Follow

- Same file-based flag pattern as task-gate (`.workflow/state/` directory)
- Same `safeJsonParse` for reading ready.json
- Same `claudeCodeAdapter.transformResult()` for output formatting
- Fail-open for routing gate (unlike task-gate which fails-closed)
  - Rationale: routing gate is a convenience enforcement; task-gate is the hard security boundary

### What NOT to Block

- Read, Glob, Grep — read-only research tools (not matched by PreToolUse)
- Edit/Write — already blocked by task-gate when no active task
- Skill — this is the routing mechanism itself
- TodoWrite — managed by todowrite-gate

### Boundaries (DO NOT MODIFY)

- `.claude/settings.local.json` — hook registrations (no changes needed, Bash already in matcher)
- `scripts/hooks/core/task-gate.js` — existing task enforcement (independent)
- `scripts/hooks/core/scope-gate.js` — existing scope enforcement (independent)
- `scripts/hooks/adapters/claude-code.js` — adapter layer (no changes needed)

## Test Strategy

- Manual: Verify follow-ups during active task work without routing
