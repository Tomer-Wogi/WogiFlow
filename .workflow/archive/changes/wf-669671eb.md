## User Story

As a team member, I want to claim tasks from the shared task queue so that two people don't accidentally work on the same task, and I can see who's working on what.

## Description

This story adds task-level operations on top of the sync infrastructure: claiming (atomic lock acquisition), releasing, assignment by admins, and a task board view. Uses the `sync_locks` table from S1 for distributed locking with TTL-based expiry.

## Acceptance Criteria

### AC1: Atomic task claiming
Given task wf-001 is in the ready queue
When member A claims it via POST `/api/sync/:projectId/tasks/:taskId/claim`
Then the task is locked to member A with a 30-minute TTL
And member A receives the task details
And the ready.json sync state reflects the claim

### AC2: Concurrent claim prevention
Given member A claims task wf-001
When member B attempts to claim the same task
Then member B receives 409 Conflict with info about who holds the lock
And member B's claim is NOT applied

### AC3: Lock TTL expiry
Given member A claims a task with 30-minute TTL
When 30 minutes pass without heartbeat
Then the lock expires automatically
And the task returns to the unclaimed pool

### AC4: Lock heartbeat extension
Given member A has claimed a task
When member A sends POST `/api/sync/:projectId/tasks/:taskId/heartbeat`
Then the lock TTL is extended by another 30 minutes
And session hooks auto-send heartbeats every 10 minutes

### AC5: Admin task assignment
Given an admin or owner
When they POST `/api/sync/:projectId/tasks/:taskId/assign` with `{userId}`
Then the task is assigned to that user (with lock)
And the assigned user sees it in their task list

### AC6: Task release
Given member A has a claimed task
When they POST `/api/sync/:projectId/tasks/:taskId/release`
Then the lock is released
And the task returns to the unclaimed pool

### AC7: Task completion syncs state
Given member A completes a claimed task
When they POST `/api/sync/:projectId/tasks/:taskId/complete`
Then the lock is released, task moves to recentlyCompleted
And sync_state for ready.json is updated
And audit_log records the completion

### AC8: Task board view
Given a project with 10 tasks in various states
When GET `/api/sync/:projectId/tasks` is called
Then it returns tasks grouped by: unclaimed, claimed (with holder), completed
And includes lock TTL remaining for claimed tasks

### AC9: Role-based task operations
Given the role hierarchy (owner > admin > member > viewer)
When a viewer attempts to claim a task
Then they receive 403 (viewers can only view, not claim)
And members can claim, admins can assign, owners can do everything

### AC10: Stale lock cleanup
Given expired locks in the database
When a cleanup job runs (or on next API call)
Then expired locks are automatically deleted
And affected tasks return to unclaimed pool
