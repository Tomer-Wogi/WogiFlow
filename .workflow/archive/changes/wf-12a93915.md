# [wf-12a93915] Add conversation mode to wogi-start triage — open-ended discussion with no side effects

## User Story
**As a** WogiFlow user
**I want** to have open-ended conversations (brainstorming, explaining, exploring ideas) without triggering task creation, file writes, or any workflow side effects
**So that** I can think through ideas with the AI before deciding whether to formalize them into tasks

## Description
Currently `/wogi-start`'s triage classifies requests into: Conversational follow-up, Exploration, Operational, Quick Fix, Bug, and Implementation. The "Exploration" category is a thin pass-through ("answer the question directly"), but many user interactions don't fit any category cleanly — brainstorming sessions, architecture discussions, "describe how X works," "what do you think about Y," rubber-ducking problems. These currently get misrouted to `/wogi-story` (because they sound implementation-adjacent) or `/wogi-research` (because they sound like questions). The fix is adding a new **Conversation** classification inside `/wogi-start`'s triage that explicitly enters a no-side-effects mode for open-ended multi-turn discussion.

## Acceptance Criteria

### Scenario 1: Brainstorming detected and enters conversation mode
**Given** the user sends a message like "What do you think about adding a caching layer?"
**When** `/wogi-start` triages the request
**Then** it classifies as "Conversation" (not Implementation or Exploration)
**And** responds conversationally without creating any tasks, stories, or files
**And** does NOT write to ready.json, request-log.md, or any state files

### Scenario 2: "Explain/describe" requests enter conversation mode
**Given** the user sends "describe how the review pipeline works" or "explain the hook architecture to me"
**When** `/wogi-start` triages the request
**Then** it classifies as "Conversation"
**And** provides the explanation directly without creating documentation files or tasks

### Scenario 3: Idea exploration without commitment
**Given** the user sends "I'm thinking about reorganizing the skills system, where would we start?"
**When** `/wogi-start` triages the request
**Then** it classifies as "Conversation" (not Implementation — note "thinking about" signals exploration, not action)
**And** discusses the approach without creating specs, stories, or modifying any files

### Scenario 4: Natural escalation from conversation to task
**Given** the user has been in conversation mode discussing an idea
**When** the user says "ok let's make a task out of this" or "let's build it" or "create a story for this"
**Then** `/wogi-start` transitions from Conversation to the appropriate action (typically `/wogi-story`)
**And** uses context from the conversation to pre-populate the story description

### Scenario 5: Conversation mode does NOT trigger for implementation requests
**Given** the user sends "add a logout button" or "fix the auth bug" (direct imperative, no hedging)
**When** `/wogi-start` triages the request
**Then** it does NOT classify as Conversation
**And** routes to the normal Implementation or Bug path as before

### Scenario 6: Conversation mode does NOT trigger task-gate violations
**Given** the PreToolUse hook blocks Edit/Write when no active task exists in ready.json
**When** the AI is in conversation mode
**Then** no Edit/Write tools are called (conversation is purely text responses)
**And** no task-gate violations are recorded
**And** no "bypass attempt" warnings are generated

### Scenario 7: Mixed conversation with mini-investigation
**Given** the user says "how does the session-start hook work? walk me through the code"
**When** `/wogi-start` triages the request
**Then** it classifies as Conversation
**And** the AI may READ files (Glob, Grep, Read) to answer the question
**And** does NOT write any files or create tasks
**And** the response explains the code flow conversationally

### Detection signals for Conversation classification

Keywords/patterns that signal conversation intent (NOT implementation):
- "What do you think about..."
- "Let's discuss / brainstorm / talk about..."
- "Describe how X works" / "Explain X to me"
- "I'm thinking about..." / "I have an idea..."
- "Help me think through..."
- "Walk me through..."
- "How would we approach..."
- "What if we..."
- "Tell me about..." / "Show me how..."
- Questions about WogiFlow's own behavior ("how does wogi-start work?")

**Distinguishing from other categories:**
| Signal | Category | Why |
|--------|----------|-----|
| "add X" (direct imperative) | Implementation | Intent to act now |
| "I'm thinking about adding X" | Conversation | Hedging — exploring, not committing |
| "does X support Y?" | Research | Needs verified factual answer |
| "what do you think about X?" | Conversation | Seeking opinion/discussion |
| "explain how X works" | Conversation | Seeking understanding |
| "fix the bug in X" | Bug | Direct imperative + broken thing |

### Behavior rules for conversation mode

1. **Allowed tools**: Read, Glob, Grep, WebSearch, WebFetch (read-only investigation)
2. **Blocked tools**: Edit, Write, NotebookEdit, TodoWrite (no file modifications)
3. **No state changes**: Don't touch ready.json, request-log.md, app-map.md, etc.
4. **No task creation**: Don't create stories, bugs, or tasks
5. **No guilt messaging**: Don't show "The user trusts you to follow WogiFlow" messages
6. **Natural exit**: User explicitly asks to formalize ("let's build it", "create a story", "make a task")

### Integration with existing routing

The Conversation category slots into the existing triage as follows:

```
Current:  Follow-up | Exploration | Operational | Quick Fix | Bug | Implementation
Updated:  Follow-up | Conversation | Exploration | Operational | Quick Fix | Bug | Implementation
```

**Exploration vs Conversation:**
- Exploration = one-shot question, expects a direct answer, done
- Conversation = multi-turn discussion, open-ended, may or may not lead to action

This is purely a prompt/instruction change in the command definition files. No new JavaScript files, no config.json changes, no hook modifications. The triage is AI-driven (prompt-based classification), not code-driven.
