## User Story

As a team member using WogiFlow, I want my project state (tasks, decisions, registries) to sync automatically across all team members, so that everyone works with the same rules, sees the same tasks, and can claim/assign work without conflicts.

## Description

Phase T2 builds on the T1 foundation (auth, teams, projects, device auth) to add the core collaboration engine: bidirectional state sync, task claiming/locking, and team presence. This is the phase that turns individual WogiFlow usage into a team tool.

The sync engine uses a file-type-aware merge strategy (append-only for logs, last-write-wins for registries, entry-level locking for tasks) with offline-first architecture.

## Architecture Decisions

### Sync Strategy (per file type)

| File | Strategy | Rationale |
|------|----------|-----------|
| `decisions.md` | Append + admin merge | Rules accumulate, conflicts resolved by admin |
| `ready.json` | Entry-level locking | Tasks claimed individually, prevent double-claim |
| `app-map.md`, `function-map.md`, etc. | Last-write-wins per entry | Registry entries are independent |
| `feedback-patterns.md` | Append-only | Patterns accumulate across users |
| `config.json` | Admin-push only | CTO/admin controls config |
| `progress.md` | Append-only per user | Each user's progress is independent |
| `roadmap.md` | Section-level merge via PIN system | Sections are independent |

### Offline-First Design

- Local state is always source of truth for current work
- Sync is background, non-blocking
- Offline changes are queued and replayed on reconnect
- Conflicts resolved by strategy (see table above)
- Cloud is source of truth for: task claiming, admin config

### DB Design

- Sync state tracked per-project, per-file with version vectors
- Server stores canonical state + change log
- Clients send diffs (not full files), server applies merge strategy
- Efficient polling via ETag/If-None-Match headers
