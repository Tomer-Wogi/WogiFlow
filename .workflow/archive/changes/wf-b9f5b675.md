# [wf-b9f5b675] State Machine Workflow Enforcement — Replace Prompt Bloat with Programmatic Phase Gating

## User Story
**As a** WogiFlow user
**I want** the workflow to be enforced programmatically through hooks, not through thousands of lines of prompt text
**So that** the AI physically cannot skip workflow steps (instead of being asked nicely not to), while using far fewer tokens per session

## Description
WogiFlow's enforcement is split between two mechanisms: programmatic hooks (which work) and prompt text in CLAUDE.md (which the AI frequently ignores). The AI skips the 15-step execution pipeline because nothing prevents it — the hooks only gate Edit/Write without a task and Bash without routing. Everything between those two gates (explore phase, spec generation, approval, criteria checks, standards checks) is prompt-only and routinely bypassed.

This story adds **phase-based tool permissions** to the existing PreToolUse hook via a lightweight state machine, strips CLAUDE.md of all text that hooks already enforce, and adds just-in-time context injection via UserPromptSubmit so the AI gets phase-specific instructions instead of the full pipeline.

**Key constraint**: This extends existing hooks — no new hook registrations, no new npm dependencies, no architectural changes. The state machine is a JSON file + ~150 lines of code in existing hook modules.

## Acceptance Criteria

### Scenario 1: Workflow state file tracks current phase
**Given** WogiFlow is installed and a session is active
**When** the workflow progresses through phases
**Then** `.workflow/state/workflow-phase.json` tracks the current phase:
  - `idle` — no active task, waiting for routing
  - `routing` — /wogi-start invoked, classifying request
  - `exploring` — explore phase agents running (research, codebase analysis)
  - `spec_review` — spec generated, waiting for approval
  - `coding` — implementation approved, actively editing files
  - `validating` — running lint, typecheck, tests, criteria checks
  - `completing` — updating logs, maps, committing
**And** the file includes `taskId`, `phase`, `updatedAt`, and `previousPhase`
**And** the file is created on first use if it doesn't exist (defaults to `idle`)
**And** stale phases auto-expire after 2 hours (reset to `idle`)

### Scenario 2: PreToolUse enforces phase-based tool permissions
**Given** the workflow is in a specific phase
**When** the AI attempts to use a tool not allowed in that phase
**Then** the PreToolUse hook returns `deny` with a message explaining what phase is active and what tools are available
**And** the phase-tool permission map is:

| Phase | Allowed Tools | Blocked (with deny message) |
|-------|--------------|----------------------------|
| `idle` | Read, Glob, Grep, Skill, Task, WebSearch, WebFetch | Edit, Write, Bash (except git status/log/diff) |
| `routing` | Skill, Read, Glob, Grep, Task | Edit, Write, Bash |
| `exploring` | Read, Glob, Grep, WebSearch, WebFetch, Task, Bash (read-only commands) | Edit, Write |
| `spec_review` | Read, Glob, Grep | Edit, Write, Bash |
| `coding` | Read, Glob, Grep, Edit, Write, Bash, Task | (all allowed) |
| `validating` | Bash, Read, Glob, Grep | Edit, Write |
| `completing` | Read, Edit, Write, Bash, Glob, Grep | (all allowed — for logs/maps/commit) |

**And** the existing task-gate, scope-gate, and routing-gate still run as before (phase gating is an additional layer, not a replacement)
**And** if `workflow-phase.json` is missing or unreadable, fall back to current behavior (fail-open for phase check only)

### Scenario 3: Phase transitions happen at well-defined points
**Given** the AI is executing a workflow
**When** specific actions complete
**Then** phase transitions occur automatically:

| Trigger | From → To |
|---------|-----------|
| `/wogi-start` skill invoked | `idle` → `routing` |
| `/wogi-start` classifies as Conversation/Exploration/Operational | `routing` → `idle` (no task needed) |
| Task moved to `inProgress` in ready.json | `routing` → `exploring` |
| Explore agents complete (or skipped for L3 tasks) | `exploring` → `spec_review` (or `coding` if no spec needed) |
| User approves spec (or auto-approved for L2/L3) | `spec_review` → `coding` |
| All acceptance criteria implemented | `coding` → `validating` |
| All validation passes | `validating` → `completing` |
| Task moved to `recentlyCompleted` | `completing` → `idle` |
| Validation fails | `validating` → `coding` (back to fix) |

**And** transitions are logged to `workflow-phase.json` with timestamps
**And** invalid transitions (e.g., `idle` → `coding`) are rejected with an error

### Scenario 4: Phase transitions are triggered from existing code paths
**Given** the phase system needs to integrate with existing hooks
**When** phase transitions need to happen
**Then** they are triggered from these existing locations:
  - `idle → routing`: In PreToolUse when Skill(wogi-start) is detected (already tracked in pre-tool-use.js)
  - `routing → exploring/coding`: In the /wogi-start skill execution (the skill writes the phase file)
  - `coding → validating`: When Stop hook fires (loop-check.js already runs here)
  - `validating → coding`: When loop-check returns "continue" (criteria incomplete)
  - `validating → completing`: When loop-check detects all criteria met
  - `completing → idle`: In task-completed.js when task moves to recentlyCompleted
  - Stale reset: In session-start.js (check for 2-hour expiry on startup)
**And** the /wogi-start skill file (`.claude/commands/wogi-start.md`) includes instructions to write phase transitions at the appropriate points
**And** no new hook registrations are needed in `.claude/settings.json`

### Scenario 5: UserPromptSubmit injects phase-specific context instead of full pipeline
**Given** the AI is in a specific workflow phase
**When** a user prompt is submitted
**Then** the UserPromptSubmit hook injects a brief, phase-specific instruction as `additionalSystemPrompt`:
  - `idle`: "Route this request through a /wogi-* command before taking any action."
  - `routing`: (no injection — /wogi-start skill handles this)
  - `exploring`: "Research phase active for {taskId}. Use only read-only tools. Do NOT edit files."
  - `spec_review`: "Spec generated for {taskId}. Wait for user approval before implementing."
  - `coding`: "Implementing {taskId}. Follow acceptance criteria. Run verification after each edit."
  - `validating`: "Validation phase for {taskId}. Run lint, typecheck, tests. Fix issues, do not add new features."
  - `completing`: "Completing {taskId}. Update request-log, maps, and commit."
**And** each injection is 1-2 sentences maximum (under 50 tokens)
**And** this replaces the ~500 token enforcement blocks currently in UserPromptSubmit

### Scenario 6: CLAUDE.md template stripped of hook-enforced content
**Given** hooks programmatically enforce task gating, routing, and validation
**When** the CLAUDE.md template is updated
**Then** the following sections are removed or reduced:
  - **Task Gating section** (lines 7-96): Reduced to 5 lines ("All requests route through /wogi-* commands. Enforced by hooks.")
  - **Workflow Violations section** (lines 246-329): Removed entirely (hooks enforce this)
  - **Universal Entry Point duplicates** (lines 203-244): Reduced to reference NLD table only
  - **Auto-Validation section** (lines 389-397): Removed (hooks auto-validate)
  - **Research Protocol details** (lines 683-735): Reduced to 3 lines ("Research protocol active. See /wogi-research.")
  - **Handling Large Requests** (lines 501-595): Moved to /wogi-story skill
  - **Continuous Learning details** (lines 606-673): Reduced to 5 lines referencing the learning system
  - **Guilt messaging**: All "MANDATORY", "NO EXCEPTIONS", "NON-NEGOTIABLE" emphasis text removed
  - **User Commands documentation**: Reduced to command table only (detailed docs load from skills)
  - **Auto-Features documentation**: Reduced to brief summary (detailed docs load from skills)
**And** the resulting CLAUDE.md is under 350 lines (down from ~1,073)
**And** the Natural Language Detection table is preserved exactly as-is
**And** File Locations, Commit Behavior, Quality Gates, and Task ID format sections are preserved
**And** no functionality is lost — everything removed is either hook-enforced or available in skill docs

### Scenario 7: Existing enforcement gates are NOT modified
**Given** the current hooks enforce task gating, scope gating, routing, and loop completion
**When** phase gating is added
**Then** ALL existing gates continue to function exactly as before:
  - `task-gate.js`: Still blocks Edit/Write without active task
  - `scope-gate.js`: Still validates edits match task scope
  - `routing-gate.js`: Still blocks Bash without /wogi-* routing
  - `loop-check.js`: Still blocks Stop until criteria complete
  - `todowrite-gate.js`: Still blocks implementation todos without task
  - `implementation-gate.js`: Still injects routing context
  - `research-gate.js`: Still detects research requirements
  - `component-check.js`: Still warns about duplicates
**And** phase gating runs BEFORE existing gates in PreToolUse (early exit if phase denies)
**And** if phase gating allows, existing gates still run (defense in depth)

### Scenario 8: Conversation and Exploration modes bypass phase gating
**Given** the user is in a conversation or exploring code
**When** /wogi-start classifies as Conversation or Exploration
**Then** the phase transitions from `routing` → `idle` (not to `exploring` or `coding`)
**And** Read, Glob, Grep, WebSearch, WebFetch work normally without phase restrictions
**And** Edit/Write are still blocked by the task-gate (no active task)
**And** the experience is identical to today — no regression for non-implementation interactions

### Scenario 9: Quick fixes and operational commands work without friction
**Given** the user requests a quick fix (L3 subtask) or operational command
**When** /wogi-start classifies as Quick Fix or Operational
**Then** for Quick Fix: phase goes `routing` → `coding` directly (skip explore/spec phases)
**And** for Operational: phase goes `routing` → `idle` and Bash is unblocked
**And** the existing routing-gate clearRoutingPending() behavior is preserved
**And** there is zero additional friction compared to current behavior

### Scenario 10: Phase system adds minimal overhead
**Given** the phase system runs on every tool call via PreToolUse
**When** performance is measured
**Then** the phase check adds less than 5ms to each tool call (single JSON file read)
**And** the workflow-phase.json file is under 500 bytes
**And** no additional npm dependencies are introduced
**And** total new code is under 200 lines across all modified files

### Architecture

```
┌─────────────────────────────────────────────────────────────┐
│  scripts/hooks/core/phase-gate.js (NEW — ~150 lines)        │
│                                                             │
│  Exports:                                                   │
│  - getCurrentPhase() → { phase, taskId, updatedAt }         │
│  - transitionPhase(from, to, taskId?) → boolean             │
│  - isToolAllowedInPhase(toolName, phase) → boolean          │
│  - checkPhaseGate(toolName) → { allowed, reason }           │
│  - resetPhase() → void (reset to idle)                      │
│                                                             │
│  Uses: fs (readFileSync/writeFileSync), path                │
│  Uses: safeJsonParse from flow-utils.js                     │
│  No external dependencies                                   │
└─────────────────────────────────────────────────────────────┘

Integration into PreToolUse flow:
  1. checkPhaseGate(toolName) ← NEW (early exit if denied)
  2. checkScopeGate() ← EXISTING (unchanged)
  3. checkTodoWriteGate() ← EXISTING (unchanged)
  4. checkRoutingGate() ← EXISTING (unchanged)
  5. checkStrictAdherence() ← EXISTING (unchanged)
  6. checkComponentReuse() ← EXISTING (unchanged)
```

### Key Patterns to Follow

- **Three-layer hooks**: Entry → Core → Adapter (per `self-maintenance.md`)
- **Security**: Use `safeJsonParse()` for all JSON reads, wrap `fs.readFileSync` in try-catch
- **Fail-open for phase gate**: If `workflow-phase.json` is missing/corrupt, skip phase check (existing gates still enforce)
- **No external dependencies**: Use Node.js built-in modules only
- **File naming**: kebab-case (`phase-gate.js`)
- **Catch variables**: Use `err` not `e`
- **Existing gates untouched**: Phase gate is additive only

### What NOT to Change

- **Do not modify** task-gate.js, scope-gate.js, routing-gate.js, loop-check.js, todowrite-gate.js, implementation-gate.js, research-gate.js, component-check.js — these work correctly and must not be touched
- **Do not add** new hook registrations to `.claude/settings.json` — use existing hook entry points
- **Do not remove** the Natural Language Detection table from CLAUDE.md — it's the core routing spec
- **Do not remove** File Locations, Commit Behavior, Quality Gates, Task ID format from CLAUDE.md — these are essential context
