# [wf-154914c4] Implement rejected-approach tagging on observations

## User Story
**As a** WogiFlow user
**I want** the agent to remember which approaches were tried and rejected
**So that** it doesn't retry failed approaches in future sessions and learns from past failures

## Description
When an agent tries approach A, fails, and switches to approach B — WogiFlow currently records this as a flat timeline. After compaction, rejected approaches vanish and the agent may retry the same failed approach next session. This feature adds `exploration_status` and `rejection_reason` columns to observations, wires tagging into capture/completion flows, and surfaces rejection warnings at task start.

## Acceptance Criteria

### Scenario 1: Schema migration adds new columns
**Given** the memory DB is opened
**When** the migration runs
**Then** observations table has `exploration_status` (TEXT, nullable) and `rejection_reason` (TEXT, nullable) columns
**And** existing observations are unaffected (null defaults)

### Scenario 2: Failed tool observations tagged as rejected
**Given** a tool execution fails (toolResponse has error)
**When** the PostToolUse hook captures the observation
**Then** the observation is stored with `exploration_status='rejected'` and `rejection_reason` set to the error message (truncated to 500 chars)

### Scenario 3: Task completion marks observations as committed
**Given** a task completes successfully
**When** the TaskCompleted hook fires
**Then** all non-rejected observations for that task are updated to `exploration_status='committed'`

### Scenario 4: Session context surfaces past rejections
**Given** a task has past rejected observations
**When** session context is gathered (at session start or task start)
**Then** rejected approaches are included in the context injection as warnings

### Scenario 5: Compact search returns exploration status
**Given** observations exist with various exploration statuses
**When** `searchObservationsCompact()` is called
**Then** results include `exploration_status` and `rejection_reason` fields

### Scenario 6: Update function allows status changes
**Given** an observation exists
**When** `updateObservationStatus(id, status, reason)` is called
**Then** the observation's exploration_status and rejection_reason are updated

### Scenario 7: Extraction promotes rejection patterns to facts
**Given** rejected observations exist for completed tasks
**When** `extractHighValueObservations()` runs
**Then** rejected observations with reasons are promoted to facts with `category='rejection-pattern'`
**And** non-rejected observations continue normal extraction (committed preferred)

### Scenario 8: Approach thrashing detection in loop check
**Given** 3+ rejected observations on the same file within the last hour
**When** `checkLoopExit()` runs
**Then** it returns a warning about approach thrashing with suggestions to try a different strategy

## Technical Notes
- **Files to change**:
  - `scripts/flow-memory-db.js` - Schema migration, storeObservation, searchObservationsCompact, getObservationsByIds, extractHighValueObservations, new updateObservationStatus()
  - `scripts/hooks/core/observation-capture.js` - Accept and pass exploration_status/rejection_reason
  - `scripts/hooks/entry/claude-code/post-tool-use.js` - Tag failed tools as rejected
  - `scripts/hooks/core/task-completed.js` - Mark task observations as committed
  - `scripts/hooks/core/session-context.js` - Query and surface rejected approaches
  - `scripts/hooks/core/loop-check.js` - Approach thrashing detection
  - `scripts/flow-memory-compactor.js` - Extract rejection patterns before purge

## Complexity
Medium-High - 7 files, schema change + wiring into multiple existing flows
