# Story: Registry Manifest Wiring — Migrate all consuming systems to dynamic registry discovery
<!-- Formerly: wf-manifest-wiring -->

**ID**: wf-927db36d
**Epic**: epic-universal-registry
**Type**: story
**Priority**: P1
**Feature**: scanner

## User Story

As a WogiFlow developer adding new registry types,
I want all consuming systems (context loaders, quality gates, hooks, instructions) to discover registries dynamically from registry-manifest.json,
So that adding a new registry automatically wires it into the entire system without touching 46+ files.

## Description

The wiring audit identified 46+ files across 7 layers that hardcode references to the three original maps (app-map.md, function-map.md, api-map.md). Without updating these consumers, new registries (schema-map, service-map, etc.) would be "dead files" — generated but never loaded into AI context, never validated by quality gates, never copied to worktrees.

This story migrates all consuming systems to read `registry-manifest.json` (generated by RegistryManager in wf-ext-registry) instead of hardcoding map names. A `getActiveRegistries()` helper provides the fallback-safe interface.

## Acceptance Criteria

### Scenario 1: Path constants use manifest
Given `flow-utils.js` currently exports hardcoded `appMap`, `functionMap`, `apiMap` paths
When the manifest wiring is complete
Then `flow-utils.js` exports a `getRegistryPaths()` function that reads the manifest
And the old path constants still exist for backwards compatibility
And new registries added to the manifest are automatically included

### Scenario 2: Context loading discovers all registries
Given `flow-auto-context.js`, `flow-section-index.js`, and `flow-context-gatherer.js` load map files
When a new registry (e.g., schema-map.md) is added to the manifest
Then context loading automatically includes it without code changes

### Scenario 3: Quality gates validate all active registries
Given `flow-done.js`, `flow-standards-checker.js`, `flow-consistency-check.js` check maps
When a new registry map exists
Then quality gates include it in their checks

### Scenario 4: Hooks handle all active registries
Given `task-completed.js` triggers post-task scans and `worktree-lifecycle.js` copies maps to worktrees
When a new registry is active
Then post-task scans include it and worktree copies include its map files

### Scenario 5: Health checks cover all registries
Given `flow-health.js` checks for map file existence and freshness
When a new registry is active
Then health checks include it

### Scenario 6: AI instruction templates use dynamic registry lists
Given `.workflow/templates/` and `.claude/commands/` reference specific map names
When templates are rendered
Then they include all active registries from the manifest
And instructions tell the AI to check all active maps, not just the hardcoded three

### Scenario 7: Backwards compatibility preserved
Given a project without `registry-manifest.json` (pre-migration)
When any consuming system runs
Then it falls back to the original three hardcoded maps
And no errors occur

## Technical Notes

### Architecture: Wiring Layers

The 46+ files are organized into 7 layers. Each layer has a migration strategy:

#### Layer 1: Path Constants & Config (3 files)
| File | Current | Migration |
|------|---------|-----------|
| `scripts/flow-utils.js` | Hardcoded `appMap`, `functionMap`, `apiMap` paths | Add `getActiveRegistries()` + `getRegistryPaths()` helpers. Keep old constants for backwards compat. |
| `.workflow/config.json` | Separate `functionRegistry`, `apiRegistry` keys | Add `registries` array (done in wf-ext-registry). Old keys still read. |
| `lib/installer.js` | Writes hardcoded config keys | Generate initial `registry-manifest.json` during install. |

#### Layer 2: Scanners & Producers (3 files)
| File | Current | Migration |
|------|---------|-----------|
| `scripts/flow-function-index.js` | Direct INDEX_PATH/MAP_PATH constants | Already thin wrapper (from wf-ext-registry). No additional changes. |
| `scripts/flow-api-index.js` | Direct INDEX_PATH/MAP_PATH constants | Already thin wrapper (from wf-ext-registry). No additional changes. |
| `.claude/commands/wogi-onboard.md` | Lists three specific maps | Template variable: list all active registries |

#### Layer 3: Context Loading (6 files)
| File | Current | Migration |
|------|---------|-----------|
| `scripts/flow-auto-context.js` | Hardcoded map file list | Read manifest, iterate all active registry map files |
| `scripts/flow-section-index.js` | Hardcoded map file list for PIN indexing | Read manifest, index all active map files |
| `scripts/flow-start.js` | Checks function-index.json and api-index.json | Read manifest, check all active index files |
| `scripts/flow-orchestrate.js` | References three maps | Read manifest for map discovery |
| `scripts/flow-context-gatherer.js` | Loads three maps | Read manifest, load all active maps |
| `scripts/flow-pattern-enforcer.js` | References three maps for pattern checks | Read manifest for dynamic map list |

#### Layer 4: Quality Gates & Validators (4 files)
| File | Current | Migration |
|------|---------|-----------|
| `scripts/flow-done.js` | `appMapUpdate` gate, hardcoded scan triggers | Generalized `registryUpdate` gate that checks all active registries |
| `scripts/flow-standards-checker.js` | STANDARDS_FILES with 3 parse functions | Read manifest, use generic parse per registry type |
| `scripts/flow-consistency-check.js` | Three separate parse functions | Read manifest, use generic parse + validate for each registry |
| `scripts/flow-health.js` | Checks three map files exist | Read manifest, check all active map files |

#### Layer 5: Hooks (3 files)
| File | Current | Migration |
|------|---------|-----------|
| `scripts/hooks/core/task-completed.js` | Hardcoded FunctionScanner + APIScanner | Call RegistryManager.scanAll() |
| `scripts/hooks/core/component-check.js` | Checks app-map only | Check all registries in 'code' category |
| `scripts/hooks/core/worktree-lifecycle.js` | Hardcoded map file list to copy | Read manifest, copy all active map files |

#### Layer 6: AI Instructions (~105 references)
| File Group | Current | Migration |
|------------|---------|-----------|
| `.claude/commands/wogi-start.md` | ~50 refs to three maps | Use template variables for registry lists |
| `.claude/commands/wogi-review.md` | References three maps in review checklist | Dynamic checklist from manifest |
| `CLAUDE.md` (via templates) | ~20 refs to three maps | Template generates from manifest |
| `.workflow/templates/*.hbs` | Hardcoded map names | Template helper `{{#each activeRegistries}}` |
| `agents/*.md` | Reference three maps | Template-generated agent personas |

**Strategy for Layer 6**: Rather than updating 105 individual references, update the **template system** (`claude-md.hbs`, `auto-features.hbs`, agent templates) to generate instructions dynamically from the manifest. Slash commands that reference maps should use a template variable pattern: `{{registryMaps}}` that expands to the current list.

#### Layer 7: Misc (4 files)
| File | Current | Migration |
|------|---------|-----------|
| `scripts/flow-export.js` | Exports three maps | Read manifest, export all active maps |
| `scripts/flow-import.js` | Imports three maps | Read manifest, import all active maps |
| `scripts/flow-checkpoint.js` | Saves three maps in checkpoints | Read manifest, save all active maps |
| `scripts/flow-context-monitor.js` | Monitors three map file sizes | Read manifest, monitor all active maps |

### Implementation Order

1. **flow-utils.js**: Add `getActiveRegistries()` and `getRegistryPaths()` helpers (foundation)
2. **Layer 3 (Context Loading)**: Highest impact — makes new maps visible to AI
3. **Layer 5 (Hooks)**: Auto-scans + worktree support
4. **Layer 4 (Quality Gates)**: Validation for new maps
5. **Layer 7 (Misc)**: Export/import/checkpoint support
6. **Layer 6 (Instructions)**: Template system updates
7. **Layer 1 (Config/Installer)**: Final config migration

### Key Design Decisions

1. **Fallback everywhere**: Every `getActiveRegistries()` call falls back to the original three maps if manifest doesn't exist
2. **Additive only**: Old hardcoded references are kept alongside dynamic ones during migration
3. **Template-driven instructions**: Rather than updating 105 individual `.md` references, the template system generates them
4. **No breaking changes**: Projects without the manifest work exactly as before

## Boundaries

Do NOT modify:
- Registry plugin classes (those are in wf-ext-registry)
- Map file formats (`.md` content structure)
- RegistryManager orchestration logic
- The three original map files themselves

## Dependencies

- **Depends on**: wf-ext-registry (needs RegistryManager and manifest generation)

## Complexity

High — Touches 46+ files across 7 system layers. Each layer needs careful migration with backwards compatibility. However, the actual code changes per file are small (replace hardcoded paths with `getActiveRegistries()` calls).
