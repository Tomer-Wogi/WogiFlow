# wf-f7d58760: long-input-pending gate misfires on sub-agent task-notifications

**Created**: 2026-05-11
**Status**: Open
**Severity**: High
**Priority**: P1
**Tags**: #bug #gate #long-input-pending #sub-agent
**Discovered From**: external session (wogiflow-cli build, 2026-05-10)
**Discovered During**: cross-project integration

## Bug Summary

The `long-input-pending` gate captures `<task-notification>` tool-result content from completed background sub-agents and treats it as a user prompt that breaches the long-input threshold. It then force-blocks Edit/Write/Bash/Skill. Combined with the gate's `Bash`-required dismissal path, this creates an unrecoverable lock in any session that uses `Agent` with `run_in_background: true`.

## META-EVIDENCE: This bug reproduced during the very session that filed it

While running `/wogi-extract-review` on the inbound bug report (the documented unblock path), the gate's allowlist permitted Bash for `flow extract-zero-loss` — but the local `scripts/flow` (v1.0.24 shell wrapper) does NOT route that subcommand to its Node implementation. The ONLY working escape was `flow long-input-pending dismiss --reason="..."`. The gate's documented recommended path was unreachable; the escape hatch was the only path that worked.

## Reproduction

### Steps to Reproduce
1. Start a Claude Code session in a WogiFlow-enabled repo.
2. Launch a sub-agent with `Agent({ run_in_background: true, ... })`.
3. Wait for the sub-agent to complete.
4. Observe `.workflow/state/long-input-pending.json` written with `promptPreview` starting with `<task-notification>`.
5. Attempt any Edit/Write — blocked.
6. Attempt to `Skill(skill="wogi-extract-review")` — runs but the underlying extraction CLI is also blocked unless on the allowlist.

### Expected Behavior
The gate should fire only on user-originated prompts. System events (`<task-notification>`, tool-result echoes, hook injections) should pass through.

### Actual Behavior
The gate fires on `<task-notification>` content and blocks all mutation tools until dismissed.

### Environment
- WogiFlow: this repo, v2.30.1
- Reported on npm `wogiflow`: latest as of 2026-05-10
- Claude Code: Opus 4.7 (1M context)

## Root Cause Analysis

### What Went Wrong?
The `UserPromptSubmit` hook (or its caller in `scripts/hooks/entry/claude-code/user-prompt-submit.js`) does not distinguish between true user input and tool-notification echoes. Anything that arrives with sufficient line count + imperative keywords triggers `markLongInputPending()` in `scripts/hooks/core/long-input-enforcement.js`.

### Why Did This Happen?
- [x] Incorrect assumption about inputs/state — assumed all `UserPromptSubmit` payloads originate from user typing
- [x] Missing edge case handling — sub-agent task-notification content wasn't considered

### Source of the Problem
- **Logic gap**: detection upstream of `markLongInputPending()` is content-based only, not source-based.
- **Missing context**: Claude Code passes a `source` field in the hook payload (referenced in `isChannelDispatchInWorker()` in long-input-enforcement.js:114). Same field can disambiguate user prompts from tool-result echoes.

---

## Fix Approaches

### Approach 1: source-aware classification at hook entry (Recommended)
**Description**: In `user-prompt-submit.js`, inspect `parsedInput.source` and skip long-input detection when source indicates `tool_result`, `task-notification`, or any non-user origin. Allowlist by content prefix: any text starting with `<task-notification>`, `<system-reminder>`, etc. is treated as system content and exempt.
**Pros**: Cleanest fix at the right layer; uses signal already available.
**Cons**: Need to enumerate all system-content tags.
**Files affected**: `scripts/hooks/entry/claude-code/user-prompt-submit.js`, possibly `scripts/hooks/core/long-input-enforcement.js` (add `isSystemOriginatedContent(text)` helper).

### Approach 2: gate allowlist expansion only
**Description**: Add more bypasses to `checkLongInputPendingGate()` so the marker is recoverable without dismiss.
**Pros**: Smaller surface change.
**Cons**: Doesn't fix the false-positive; just makes recovery less painful. The marker still spams the user.

### Chosen Approach
Approach 1. The detection layer is where the bug lives; fix it there.

**Given** the user types a 50-line prompt with 6+ items
**When** `UserPromptSubmit` fires with `source` indicating user input

**Given** the marker is set legitimately
**When** the user invokes `Skill(wogi-extract-review)` or `flow long-input-pending dismiss`
