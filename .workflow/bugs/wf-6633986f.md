# wf-6633986f: Config inconsistency: communitySync.enabled and community.sync.enabled contradict each other

**Created**: 2026-03-11
**Status**: Fixed
**Severity**: High
**Priority**: P1
**Tags**: #bug #config #community-sync

## Bug Summary

The config system allows `communitySync.enabled: true` and `community.sync.enabled: false` to coexist with opposite values. The migration logic in `flow-config-loader.js:227` silently skips conflict resolution when both keys exist, and the runtime in `flow-community-sync.js:60` reads only `communitySync.enabled`, so community sync runs as ON despite `community.enabled: false` and `community.sync.enabled: false` both saying otherwise.

## Reproduction

### Steps to Reproduce
1. Have a config where `community.enabled: false` and `community.sync.enabled: false` (from defaults in `flow-config-defaults.js:841-853`)
2. Run onboard or any operation that sets `communitySync.enabled: true` at the top level
3. Load config via `getConfig()` — migration at line 227 checks `!config.communitySync`, finds it exists, skips migration
4. Call `getSyncConfig()` in `flow-community-sync.js:56` — reads `config.communitySync.enabled: true`

### Expected Behavior
`community.enabled: false` should act as a master toggle that forces `communitySync.enabled = false`. When both keys exist with different values, the migration should warn and resolve the conflict.

### Actual Behavior
- Migration silently skips (guard `!config.communitySync` is false)
- `community.sync.enabled: false` is ignored
- `community.enabled: false` is never checked
- Runtime reads `communitySync.enabled: true` — sync is ON

### Environment
- Node/Runtime: Node.js (per package.json)
- Version: wogiflow 1.9.4

## Root Cause Analysis

### What Went Wrong?

Three compounding issues in the config pipeline:

1. **Migration guard doesn't detect conflicts** (`flow-config-loader.js:227`): The guard `!config.communitySync` only migrates if the target key is absent. If both keys exist with different values, the old key is silently ignored.

2. **No master toggle enforcement**: `community.enabled: false` (from `flow-config-defaults.js:841`) is never checked by `getSyncConfig()` in `flow-community-sync.js:56-62`. The runtime spreads `config.communitySync` directly without checking the parent toggle.

3. **Runtime reads only one key** (`flow-community-sync.js:60`): `getSyncConfig()` uses `config.communitySync || {}` — never consults `community.sync` or `community.enabled`.

### Why Did This Happen?

- [x] Missing edge case handling
- [x] Incorrect assumption about inputs/state
- [ ] Race condition / timing issue
- [ ] External dependency failure
- [x] Configuration/environment issue
- [ ] Prompt/instruction unclear or ambiguous

### Source of the Problem
- **Logic gap**: The migration assumed `communitySync` and `community.sync` would never coexist. Story wf-1d612670 (Config Consolidation) intended to merge them into a single key, but the migration only handles the "old key exists, new key doesn't" case.
- **Missing context**: No validation that `community.enabled` should gate all child features. The hierarchical dependency was implied by naming but never enforced in code.

## Fix Approaches

### Approach 1: Master toggle + conflict detection (Recommended)
**Description**:
1. In `getSyncConfig()`, check `community.enabled` first — if false, force sync disabled
2. In `applyConfigCompatShim()`, detect when both keys exist with conflicting `.enabled` values and warn
3. After migration, delete `community.sync` to prevent future confusion

**Pros**: Fixes all three root causes, respects hierarchical config intent, warns on conflicts
**Cons**: Slightly more migration logic
**Files affected**: `scripts/flow-config-loader.js`, `scripts/flow-community-sync.js`

### Approach 2: Unify to single key + remove nested
**Description**: Remove `community.sync` from defaults entirely. Move all sync config to `communitySync` only. Strip `community.sync` during migration unconditionally.

**Pros**: Eliminates duplication permanently
**Cons**: Breaking change for configs that rely on `community.sync`. Doesn't address the master toggle issue.
**Files affected**: `scripts/flow-config-loader.js`, `scripts/flow-config-defaults.js`, `scripts/flow-community-sync.js`

### Chosen Approach
**Approach 1** — it fixes the immediate bug (master toggle + conflict warning) without a breaking migration, and the conflict detection pattern can be extended to the other 14 similar migrations in `applyConfigCompatShim()`.

## Prevention & Learning

### How to Prevent Similar Bugs
1. Config migration shims should always include conflict detection — not just "skip if target exists"
2. Hierarchical config keys (parent.child) should enforce parent toggles in readers
3. The systemic pattern affects 14 other migrations in `applyConfigCompatShim()` — consider a shared `migrateConfigKey(config, source, target)` helper that handles conflict detection

### Learnings to Capture
- [ ] Pattern to add to decisions.md: Config migration must handle conflict case (both keys exist, different values) — warn and prefer newer key
- [ ] Pattern to add to decisions.md: Hierarchical config toggles (e.g., `X.enabled`) must be checked by all readers of child keys
