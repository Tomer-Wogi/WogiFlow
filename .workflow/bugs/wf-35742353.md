# wf-35742353: Gate cascade — Stop hook + research-required + long-input-pending fire same turn with conflicting remediations

**Created**: 2026-05-11
**Status**: Open
**Severity**: Medium
**Priority**: P1
**Tags**: #bug #gate-cascade #ux #conflicting-remediation
**Discovered From**: external session (wogiflow-cli build, 2026-05-10)
**Discovered During**: cross-project integration

## Bug Summary

Three gates can fire on the SAME turn with mutually exclusive remediation instructions: the Stop hook says "escalating to user", the long-input-pending gate says "invoke /wogi-extract-review", and the routing-enforcement gate says "invoke /wogi-start NOW". The user sees a wall of system-reminder text and can't tell which to act on. No priority order, no single recommended next action.

## Reproduction

### Steps to Reproduce
1. Have a session where multiple gates have armed conditions (e.g., long-input pending + diagnostic-prompt classifier + bypass-counter elevated).
2. Submit a prompt that satisfies all three triggers.
3. Observe three `<system-reminder>` blocks injected, each demanding a different action.

### Expected Behavior
One remediation surfaced at a time. The gates have a documented priority order. Other gates are suppressed (or noted but not actionable) until the highest-priority one is resolved.

### Actual Behavior
All three fire. Three blocks of red-flag text. User has to manually triage which to do first.

### Environment
- WogiFlow: this repo, v2.30.1
- Reported on npm `wogiflow`: latest as of 2026-05-10

---

## Root Cause Analysis

### What Went Wrong?
Gates were added independently over time. Each one's enforcement message was designed assuming it was the only gate firing. There's no orchestration layer that knows about the full set of armed gates and picks the most important one.

### Why Did This Happen?
- [x] Logic gap: no inter-gate prioritization
- [x] UX gap: each gate is a "perfect citizen" individually but they collide at the integration point

### Source of the Problem
- **Logic gap**: `scripts/hooks/entry/claude-code/stop.js` calls each gate independently; whichever wants to inject text does so. `user-prompt-submit.js` similarly.

---

## Fix Approaches

### Approach 1: gate priority + single-surface orchestrator (Recommended)
**Description**: Define a strict priority order for remediation gates. When multiple gates would fire, only the highest-priority one surfaces its remediation. The others either (a) wait until the user resolves the top one, OR (b) annotate the top remediation with "and N other issues queued".
**Pros**: Clean UX. The user has one clear next step.
**Cons**: Need to pick a priority that's right for the common case.
**Files affected**: `scripts/hooks/entry/claude-code/stop.js`, `scripts/hooks/entry/claude-code/user-prompt-submit.js`, possibly a new `scripts/hooks/core/gate-orchestrator.js`.

### Approach 2: gate consolidation — show all but with explicit priority
**Description**: Surface all three, but with a "RESOLVE THIS FIRST" header on the top-priority one and "WAITING" headers on the rest.
**Pros**: Less invasive.
**Cons**: Still a wall of text; the user has to read more.

### Chosen Approach
Approach 1.

### Proposed Priority Order
1. **long-input-pending** (force) — user prompt isn't captured; everything downstream is suspect. Fix this first.
2. **routing-enforcement** — task not assigned; no work is tracked. Fix second.
3. **research-required** — diagnostic prompt needs evidence. Fix third.
4. **Stop hook silent-halt / question-classifier** — bottom of the stack; the others usually subsume this.

## Acceptance Criteria

### Scenario 1: multiple gates armed, single remediation surfaced
**Given** long-input-pending marker is set AND routing flag is armed AND research-required marker is set
**When** the assistant turn fires Stop hook
**Then** ONE remediation is surfaced (the long-input-pending one per priority), and the others are noted as "queued" without their full remediation prose.

### Scenario 2: priority is documented
**Given** a contributor wants to add a new gate
**When** they read the gate-orchestrator docs
**Then** the priority order is documented and they know where their new gate slots in.

### Scenario 3: resolving the top gate surfaces the next
**Given** the long-input-pending marker is cleared
**When** the next assistant turn fires
**Then** the routing-enforcement remediation surfaces (now top of queue).
