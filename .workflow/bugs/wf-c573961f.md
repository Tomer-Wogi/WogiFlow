# wf-c573961f: Task-gating gate consults 5+ drifting state sources

**Created**: 2026-05-11
**Status**: Open
**Severity**: High
**Priority**: P1
**Tags**: #bug #task-gate #state-sources #single-source-of-truth
**Discovered From**: external session (wogiflow-cli build, 2026-05-10)
**Discovered During**: cross-project integration

## Bug Summary

After creating a bug via `./scripts/flow bug "..."` and updating four known "active task" state files to point at the new task, the task-gating gate still rejected Edits with `no_task_auto_create_disabled`. At least a 5th state source is consulted that the user/agent could not discover. This makes the gate impossible to satisfy without source-spelunking and indicates that "active task" has no single source of truth.

## Reproduction

### Steps to Reproduce
1. Run `./scripts/flow bug "..."` (creates wf-XXXXXXXX in ready.json, status=Open).
2. Manually edit four state files to point at the new task:
   - `.workflow/state/workflow-phase.json` → `phase: "coding"`, `taskId: "wf-XXXXXXXX"`
   - `.workflow/state/ready.json` → move task to `inProgress[]`
   - `.workflow/state/session-state.json` → `currentTask.id = "wf-XXXXXXXX"`
   - `.workflow/state/durable-session.json` → `taskId = "wf-XXXXXXXX"`
3. Attempt to Edit any source file.
4. Gate rejects with `no_task_auto_create_disabled`.

### Expected Behavior
Either (a) the gate accepts after the documented state files are updated, OR (b) there's a single canonical "active task" state with a documented schema.

### Actual Behavior
Gate rejects despite all four documented state files agreeing. A 5th source — undiscovered — wins.

### Environment
- WogiFlow: this repo, v2.30.1
- Reported on npm `wogiflow`: latest as of 2026-05-10

## Root Cause Analysis

### What Went Wrong?
The "active task" concept is spread across multiple JSON files (`workflow-phase`, `ready`, `session-state`, `durable-session`, and at least one more). The task gate likely consults memory blocks or an in-process cache that wasn't updated when state files were rewritten externally.

### Why Did This Happen?
- [x] Logic gap: no documented schema for "what makes a task active"
- [x] Race-condition risk: multiple writers, no single reader
- [x] Missing edge case: external state-file edits aren't picked up by the gate's source-of-truth

### Source of the Problem
- **Logic gap**: callers (CLI commands, hooks, manual edits) each touch a different subset of state files. The gate consults its own subset. The intersection is empty for some paths.

## Fix Approaches

### Approach 1: consolidate "active task" to a single source of truth (Recommended)
**Description**: Designate ONE file (e.g., `.workflow/state/active-task.json`) as the canonical "what task is active right now". Every other place that currently records this becomes a denormalized cache that reads from the canonical file. The task gate consults only that file. Schema documented in CLAUDE.md or `.workflow/state/SCHEMAS.md`.
**Pros**: Fixes the bug class, not just this instance. Makes external tooling (like the original bug report's manual sync attempt) succeed.
**Cons**: Migration: existing readers/writers need updating.
**Files affected**: `scripts/hooks/core/task-gate.js`, `scripts/flow-session-state.js`, `scripts/flow-memory-blocks.js`, `scripts/flow-utils.js`, plus all CLI commands that mutate task state.

### Approach 2: document the 5th source and add it to the manual-sync recipe
**Description**: Just identify what was missed and document it.
**Pros**: Smallest change.
**Cons**: Doesn't fix the underlying drift. Same bug will reappear next time someone adds a 6th state file.

### Chosen Approach (2026-05-11, scope confirmed by user)

**L2 scope** — diagnostic + minimal fix:
1. Trace the task-gate (`scripts/hooks/core/task-gate.js`) read-path; identify ALL state sources it consults.
2. Document the full state-source list in `.workflow/state/SCHEMAS.md` (create if needed) or in a header comment on `task-gate.js`.
3. Fix the immediate symptom: ensure all sources the gate consults are writable through documented CLI / hooks (no "hidden" source).
4. If a 5th source exists that's in-process-only (memory cache, etc.), either invalidate it on external state-file change OR fix the gate to re-read from disk every check.

**Out of scope (deferred to follow-up epic)**:
- Designating a single canonical `active-task.json` and migrating all readers/writers to it. This is the full Approach 1 from earlier draft — confirmed L1+ scope by the user during /wogi-bulk planning on 2026-05-11. Filed as follow-up: see the bug-report author's "consolidate" recommendation, which remains the long-term direction.

The L2 fix resolves the user-facing pain (the gate becomes satisfiable through documented action) without committing to the system-wide refactor in this session.
